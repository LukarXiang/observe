## 1. 回测账本自己写，不用 PyBroker（2026-09-28）

**背景**：旧版需求把 PyBroker 定为主回测候选，要求先做能力验证。
**决定**：自己实现日频账本（见 `modules/16-回测账本.md`），PyBroker 不作为依赖。
**理由**：读 PyBroker 源码确认它没有分红送转、当日买入次日才能卖、整手买入、涨跌停这些 A 股必需的概念；它的轮动逻辑还会在证券离开选择窗口时自动平仓。
要补齐这些，适配层里就得自己算大部分账——等于写了两套账。日频、只做多、开盘成交的账本本身不复杂，核心约三四百行，且能逐条用手算用例核对。
**放弃**：PyBroker、rqalpha 整体接入（rqalpha 规则最全，但需要按它的数据格式准备整套数据包，且有「按当根成交量限量」「退市按市值退现金」等不符合本项目口径的默认行为）。
**重新考虑**：需要分钟级撮合或盘中事件时。

## 3. 用 pandas 3，BaoStock 结果集自己逐行读（2026-09-28）

**背景**：BaoStock 0.9.4 的 `get_data()` 在结果翻页时调用 pandas 2.0 已删除的方法，长历史查询报错。
**决定**：保留 pandas 3.0.6；本项目的 BaoStock 适配器用 `rs.next()` + `rs.get_row_data()` 逐行读取。
**放弃**：降级到 pandas 1.x（其他依赖都要求 pandas 2 以上）；修改第三方包源码（升级时会被覆盖）。

## 4. 数据源分工（2026-09-28，依据 `01-数据源实测报告.md`）

**决定**：

| 数据 | 主源 | 核对源 |
| --- | --- | --- |
| 交易日历 | BaoStock | 新浪（经 AKShare） |
| 历史在市证券（历史股票池的底） | BaoStock 按日期取的全市场日线（停牌股也有一行） | BaoStock 某日证券清单、交易所退市清单（经 AKShare） |
| 证券主数据（上市、退市日期） | BaoStock | 交易所清单（经 AKShare） |
| 日线（原始价、停牌、ST、换手、估值） | BaoStock 按日期取全市场 | 新浪、腾讯（经 AKShare） |
| 复权因子 | BaoStock | 由公司行动独立推算后比对 |
| 现金分红、送转、配股（除权除息日与金额） | 通达信除权除息（一次取全历史，含已退市股） | BaoStock 分红表、新浪分红表 |
| 现金分红到账日 | BaoStock 分红表（只查有现金分红的「证券 × 年份」） | 缺失时按除息日处理并标为假设值 |
| 历史股本变化 | 通达信除权除息 | — |
| 5 分钟线（2020 年起） | BaoStock | 抽样用通达信逐笔合成核对 |
| 指数日线 | BaoStock | 新浪 |

东方财富只在其他上游缺数时作补充，不作任何数据的主源。free-stockdb 在你决定运行其更新程序、并通过与 BaoStock 的比对审计之前，不进入分工表；通过后按「外部导入」接入，优先用于补 2020 年以前的退市股分钟数据和 1 分钟线。
**理由**：BaoStock 有「按日期取全市场」这个其他源没有的能力，返回的全市场日线里停牌股和后来退市的股票都在，且带逐日 ST 与停牌标记，分红表带到账日；通达信除权除息一次取一只股票的全部历史，速度是 BaoStock 分红表的上百倍；
东方财富对程序化访问拦截明显；2020 年以前的 5 分钟线见决策 16。
**重新考虑**：你提供外部长历史数据时，作为「外部导入」源加入，按同样的审计流程与主源比对后再决定分工。

## 5. 存储：Parquet 文件 + DuckDB 查询，SQLite 只存小表，不部署数据库服务（2026-09-28，同日补充对照与实测）

**决定**：
- **行情等大表**（日线、5 分钟线、因子、预测、账本明细）存 Parquet 文件：日线按年、5 分钟按月分区，文件内按证券、时间排序，zstd 压缩；分区写入后不改，快照是一个 JSON 清单。
- **查询**用 DuckDB 直接读 Parquet（进程内的分析型 SQL 引擎，不需要启动服务），前端接口和数据审计都走它；研究代码直接用 pandas 读分区。
- **小表**（任务队列、实验登记）各用一个 SQLite 文件。

**参考项目怎么做**（均读源码核实）：

| 项目 | 行情存储 | 元数据 | 取舍 |
| --- | --- | --- | --- |
| qlib | 自定义二进制：每只证券每个字段一个 `.bin` 文件（`qlib/data/storage/file_storage.py`），日历、证券清单为文本 | 文本文件 | 读单只快；但全市场横截面要打开上万个小文件，格式不透明、难核对 |
| zipline | bcolz 列式文件存日线和分钟线（`zipline/data/bcolz_*_bars.py`） | **SQLite** 存复权与证券信息（`adjustments.py`） | 与本项目思路最接近：大表列式文件 + 小表 SQLite；bcolz 已停止维护，Parquet 是它的现代替代 |
| rqalpha | HDF5 数据包（`rqalpha/data/base_data_source/storages.py`，h5py），部分 numpy 与 pickle 文件 | 同左 | 数据包由官方整体发布、整包更新，不适合自己增量写入 |
| vnpy | 可换数据库：默认 SQLite，另有 MySQL、PostgreSQL、MongoDB、DolphinDB、TDengine 适配 | 同一数据库 | 面向实盘逐条写入；按行存储的数据库做全市场横截面分析慢 |
| vnpy.alpha | 每只证券一个 Parquet 文件（`vnpy/alpha/lab.py`） | JSON | 格式对，但按证券分文件，全市场某一天要读几千个文件；本项目改为按时间分区 |
| hikyuu | HDF5（默认）/ MySQL / SQLite / 直读通达信文件（`hikyuu_cpp/hikyuu/data_driver/kdata/`） | MySQL / SQLite | C++ 引擎自带，偏交易系统 |
| PyBroker | 不存历史，只用 diskcache 缓存数据源结果（`pybroker/cache.py`） | — | 缓存思路可借鉴，不是存储方案 |
| free-stockdb | LevelDB 键值库 + zstd，自带 C++ 服务 | 同左 | 闭源，需常驻进程 |

**本机实测**（`scripts/probe/probe_db.py`，模拟数据，规模按本项目真实需要：日线 5500 只 × 2005 年起约 1854 万行按年分区；5 分钟 1000 只 × 2020 年起约 8434 万行按月分区）：

| 查询 | 耗时 |
| --- | --- |
| 日线：一只股票全历史（前端看 K 线） | 0.07 秒 |
| 日线：某一天全市场（横截面） | 0.10 秒 |
| 日线：2024 年以来全市场 20 日滚动均值（约 363 万行窗口计算） | 约 2 秒 |
| 5 分钟：一只股票一年 | 0.03 秒 |
| 5 分钟：某一天全池 | 0.09 秒 |
| 5 分钟：一年全池算日内特征（实现波动、尾盘收益，产出 26 万行） | 约 1.1 秒 |
| pandas 一次读入全部日线 7 列 | 0.5 秒，内存 1.2 GB |
| pandas 读一个月 5 分钟全池 | 0.04 秒，内存 0.07 GB |

模拟数据比真实数据好压缩，磁盘占用以实测报告第十四节为准（真实数据下日线约 1 GB、2020 年起 5 分钟全池约 1.6 GB）；查询耗时量级不受影响。

**理由**：本项目是单人、单机、以「批量读、按时间或按证券切片」为主的研究负载，不是多人并发写入的业务系统。列式文件 + 进程内查询在这种负载下
已经是亚秒级，同时文件可以直接复制、备份、按内容指纹做快照，这是数据库服务很难做到的。
**放弃**：MySQL / PostgreSQL（要装服务、维护账号备份，按行存储做横截面分析慢）；ClickHouse、DolphinDB 等时序/分析型数据库服务（性能强，但在本机规模下没有必要，
且增加一个常驻服务）；qlib 二进制格式；每只证券一个文件。
**重新考虑**：需要多人同时写入，或单表超过数十亿行且查询明显变慢时（例如将来存全市场 1 分钟线），再评估 ClickHouse 或 ArcticDB。

## 6. 因子和标签用后复权价，账本用原始价（2026-09-28）

**理由**：后复权价的历史值不随以后的分红而改变，今天重算的历史因子与当年一致；账本必须按真实成交价和真实股数记账。
**放弃**：前复权价（每次分红都会改写全部历史价格，因子缓存和旧实验会悄悄失效）。

## 7. 因子表达式用语法树白名单解析，不用 eval（2026-09-28）

**理由**：`eval` 能执行任意代码；白名单解析同样简单，还能顺便推算回看天数和依赖字段。vnpy 的做法不照搬。

## 8. 评价指标自己实现，外部库只作核对（2026-09-28）

**理由**：全项目一套口径（例如 IC 与秩 IC 分开命名、年化天数显式配置）；alphalens、quantstats 的默认口径与本项目要求有出入，且依赖较重。

## 9. 前后端：FastAPI + Vite/React/TypeScript/ECharts，一个进程托管（2026-09-28）

**背景**：你要求前后端和全部逻辑都独立设计实现，以满足定制需求。
**决定**：研究核心是一个不认识 HTTP 的 Python 包；FastAPI 薄薄包一层；前端是 Vite 单页应用，构建后由 FastAPI 托管。写数据的任务进单进程队列。
**理由**：与你 bidding-docs、bidding-game 的技术栈一致；单机自用不需要服务端渲染。
**放弃**：Next.js（本场景用不到服务端渲染）；Streamlit/Dash（快，但定制空间小，与「定制化」的要求不符）。

## 10. 配股按「不参与认购」处理（2026-09-28）

**背景**：旧版需求要求遇到不支持的配股就阻断正式评价；但 2006–2015 年配股不少见，全部阻断会让大量回测无法出正式结果。
**决定**：账本默认持有人不参与配股——股数不变，除权价下跌造成的损失如实计入净值。报告限制说明里列出受影响的持仓和日期。
**理由**：这是一个完全确定、可手算的真实结果（不认购的投资者就是这个结局），不是猜测；而且偏保守。
**重新考虑**：要研究「参与配股」的情形时，另加一个执行配置。

## 11. 第一版只启用沪深主板（2026-09-28）

**理由**：创业板（2020-08-24 起涨跌幅从 10% 改为 20%）、科创板（200 股起买、1 股递增）、北交所（代码迁移）都有独立的规则历史，

## 12. 所有网络请求不走系统代理（2026-09-28）

**背景**：本机设置了 `127.0.0.1:7897` 代理，且通过环境变量对所有请求生效；实测经代理访问东方财富直接失败。
**决定**：本项目的请求会话一律显式关闭代理。

## 13. BaoStock 全机单会话（2026-09-28）

**背景**：实测两个进程同时用 BaoStock 时，一个进程登出会把另一个正在下载的进程踢下线（匿名会话在服务端共享）。
**决定**：所有用到 BaoStock 的任务只能经任务队列顺序执行；命令行直接执行时先检查队列里没有正在运行的 BaoStock 任务。

## 14. 交易日历以 BaoStock 为准，不用 exchange_calendars（2026-09-28）

**理由**：exchange_calendars 的上交所日历只从 2006-09-28 开始；BaoStock 与新浪日历都从 1990-12-19 开始，交易日数一致（截至 2026 年底共 8797 天）。
交易时段（上午 9:30–11:30、下午 13:00–15:00、9:15–9:25 集合竞价）写成规则表。

## 15. 包名 `observe`（2026-09-28）

与仓库名一致。命令行入口同名：`observe ...`。旧版需求里的 `qresearch` 不再使用。

## 16. 分钟数据只用 BaoStock 2020 年以后的 5 分钟线（2026-09-28）

**背景**：你的研究偏低频（日频、周频调仓的选股），分钟数据只用来算日内特征。实测 BaoStock 5 分钟线从 2020-01-02 开始、含这期间退市的证券；
更早的只能用通达信逐笔自己合成，精度 96%–100%，但缺 2020 年以前退市的 112 只股票，且早年有缺失的日子。
**决定**：第一版分钟数据只下载分钟股票池 2020 年以后的 BaoStock 5 分钟线；分钟特征的对照实验只在 2020 年以后进行。
通达信逐笔合成 2020 年以前的 5 分钟线降为「按需扩展」；1 分钟线不下载历史。
**理由**：口径统一、没有幸存者偏差、流程简单；约 6.7 年足够做一次滚动对照实验，先回答「分钟特征到底有没有增量」，有增量再考虑拉长历史。
**放弃**：第一版就合成 2020 年以前的数据（工作量大，且结果带幸存者偏差）。
**重新考虑**：分钟特征在 2020 年以后被证明有稳定增量、需要更长历史检验时；或你提供了含退市股的早年分钟数据时。
