## 方案比较

| 方案 | 做法 | 工作量与风险 |
| --- | --- | --- |
| A：Git原生逐路径白名单，最小改动 | 对原`data/catalog/`、快照、审计等指定文件开放追踪 | 改动少，复用所有原路径；运行程序会修改被追踪的latest和登记文件，多机切分支可能改变活跃元数据，历史目录容易误加入 |
| B：Git追踪专用元数据导出目录，推荐 | 仅开放`data/metadata/`，由清单导出原件或派生摘要，运行目录继续忽略 | 增加一个导出/核验脚本；首期约数MiB至十余MiB，避免运行引擎直接写Git追踪文件，跨机只读浏览边界明确 |
| C：Git LFS或DVC管理大数据 | 增加大对象或数据版本服务、远端存储与拉取流程 | 适合以后频繁跨机获取大表，但本次“知道当前情况”的需求不需要引入存储服务，当前也没有已核实的LFS/DVC远端 |

三者都使用Git原生追踪规则；B只新增针对现有冻结文件的导出和检查，不引入第二套数据存储或实验登记数据库。已有`Store`不可变分区、`archive_strategy_progress.py`阶段归档、`prepare_handoff.py`打包/校验继续复用。当前建议B；如果后续需要自动下载大数据，再单独评估C及实际存储位置。

JSON不是追踪标准。订单、净值或累计全量备份即使是JSON仍属于载荷；选定manifest、摘要和字典才属于Git元数据。原始资料、数据表和已有完整实验从不因为导出或Git容量控制而删除。

## 跨机后的三种状态

状态按每个对象及复现依赖集合登记，而不是给整台机器一个笼统“可用”。

1. `metadata_only`：Git目录/摘要存在，载荷尚未迁入。可以阅读策略状态和结论；完整性、数据可用性及可复现性均不能判为通过。
2. `payload_partial`：部分来源、快照或分区存在。输出准确的缺失/冲突路径、实验ID及所需数据包；阻断相应复现，不联网下载新数据冒充旧输入。
3. `payload_verified`：对应清单中的输入和实验载荷完成字节核验，登记库重建后可尝试离线复现。实际重跑match与否另记，载荷齐全本身不证明经济输出相同。

读取关系如下；元数据导出工具不会写回Store或旧实验：

    repo原始来源 + data冻结分区/实验/研究证据
                         |
                   只读提取与校验
                         |
                    data/metadata ---- Git ---- 新电脑先阅读
                         |
                   包清单和缺失报告
                         |
            数据包单独迁移并核验 --> runs index --> reproduce

数据包位置只有在确实可获取并核实时才登记为可用。当前只有旧2026-10-04交接方案和部分原机凭据；不能据此宣称覆盖本机当前发布批次及所有67个父运行。新包生成前记为`not_packaged`，旧包或来源在本机缺失记为`missing_local`，地址未知记为`location_unknown`。不编造下载链接或共享盘位置。

## 实施步骤与验收

### 第一步：建立可提交的基线

审查当前未追踪代码、配置、脚本、测试、67个handoff文件及70个tasks文件，形成明确的待提交文件清单；保留既有未提交改动。首批元数据将超过8个文件，多数为静态JSON和说明，不引入新服务。检查当前已验收63批检查点`20261007-203501-128a`与进行中64批`20261007-205221-0512`，导航分别记录两者，不能仅按latest日期选“完成状态”。

交付：首批文件白名单及来源/SHA，核实当前发布`20261006-145049-5ceb`与当前快照`20261006-145049-e06c`。本机不存在的远程来源、成员表和快照保持缺失。

### 第二步：修改忽略规则并实现导出

将根`/data/`排除规则改为忽略`data/`直属内容，再明确开放`data/metadata/`及其已登记导出文件；`repo/`和其余运行目录仍排除。不使用整个data的JSON通配放行或`git add -f data`。

新增一个`scripts/export_research_metadata.py`，提供只读导出与metadata/payload两级核验，复用现有JSON读写、SHA、路径校验和实验读取函数。新增对应聚焦单元测试。避免为新导出功能修改Book、Store发布、指标算法或已有实验格式。

初次导出选定当前及上一已验收策略目录、现有财务导入版本、当前发布副本、实际存在的引用快照、67父运行摘要和批次证据索引。源校验失败时中止，先写独立新导出目录，全部成功后才更新导航；不产生指向半成品的index。相同导出逻辑内容不产生时间戳噪声；同ID同内容幂等，同ID异内容拒绝覆盖。

原件使用SHA去重、字典每导入仅存一次；不复制每阶段的sources/runs累计大表。新目录默认单文件5 MiB、单批新增20 MiB审核阈值，Git中的metadata工作树目标50 MiB内；这些是需要审查的增长阈值，不自动截断、丢弃或清理历史。超限时拆分合法对象或把完整凭据转入包、留下摘要和SHA索引。Git对象历史会累积，工作树阈值不等于仓库历史大小阈值，须另监测历史增长。

交付：导出工具、当前metadata文件集、README、白名单及被排除清单，所有必要引用可在metadata中解析或准确标记为外部载荷。额外更新现有README/AGENTS/文档索引并生成当前状态页，形成“目标→任务→来源→变体→配置/代码→实验→成本/基准→证据→限制→下一步”的可追溯关系；操作规范按LLM续接规范验收。

### 第三步：建立迁移包登记

复用`prepare_handoff.py`的快照/分区并集和拒覆盖机制，为当前发布创建新计划。载荷按用途分组：原策略来源、行情/复权/事件/日历、财务表、已验收交易实验、研究/失败证据；只阅读进度无需任何载荷包。

生成包时实际记录包ID、文件集合、大小、SHA、快照/实验列表和保管位置。不同包引用同一输入可以复用明确SHA相同的文件；缺少旧远程载荷时不能把当前包标成全历史完整。完整历史目录继续保存在原机/归档，首期不为了Git追踪把全部历史重打包。

交付：对应当前状态的真实plan/manifest/receipt及包可用性；打包失败也留档，metadata阅读能力不依赖打包成功。

### 第四步：验证只有Git的新电脑体验

在独立临时目录构造只有代码、文档及metadata的工作树，运行元数据核验：不读取原机绝对路径、不联网、不创建活跃PUBLISHED、不依赖repo/Parquet/SQLite，也能看完695来源、当前进度、14代表配置和每项阻断原因。检查明确报告缺载荷，而不是返回“数据齐全”。按LLM规范的固定问题做独立阅读验收，要求事实回答逐项引用仓库证据；检查能解释12来源/14配置/67父运行和211验收审查/213进行中审查的区别，能识别已批准变体、待回复问题及不能报告的BP阻断收益。另覆盖财务和分钟研究状态，不能只以策略批次数代表整个项目进展。

## 必要验证与故障处理

使用Git自带`git check-ignore`验证白名单及排除规则，不额外安装LFS/DVC或依赖。现有Git2.43.0、WSL解释器和`prepare_handoff.py`已核实；导出/阅读不需要任何外部API、账号或密钥。载荷的跨机保管位置尚未指定，不阻碍元数据导出，包生成后按实际位置登记。

实施测试覆盖：来源目录/结果正常导出；repo和数据全缺仍能只读浏览；缺一个分区或一个复现实验准确阻断；byte SHA与逻辑指纹混用拒绝；同ID覆盖拒绝；导出中断及并发导航不出现半成品；路径越界/符号链接拒绝；绝对路径保留但导航不用；blocked/失败/被替代实验不计完成；声明式无report.json时读取实际metrics/status；重复导出无无意义diff；超阈值文件不误入Git；新电脑metadata索引与本机当前发布不同不自动切换Store。

检查导出脚本及聚焦测试的Ruff/pytest，运行`git diff --check`及拟提交文件清单/大小检查。修改只涉及导出、忽略规则、文档与元数据时无需重复全量策略回测；迁移验收做一个所选真实离线复现。实现完成后按check技能审查，审查范围只针对本功能及关联变更。

外部接口失败时仍能依现有摘要阅读结论；所需包不可获取时列缺口并阻断复现。规模增长时按SHA和run_id复用对象、仅里程碑导出；不保存每批重复的全量目录。回退时停用导出及新追踪规则即可，旧来源、实验和分区从未修改，不需要重置或删除数据。Git导航发生多机冲突时保留双方不可变对象，重新核验后选明确的验收里程碑，不把不同机器的活跃PUBLISHED合并成一个运行状态。
